The database behind the loop

21 tables in five groups, generated from the running backend. The raw extract (341 columns per member) is loaded as received and typed; the Studio builds cohorts and campaigns on top of it; the nightly run scores members by the CCC rulebook and builds care plans; the portal records calls and outcomes, which the next run reads back. Sample rows follow one demo day: the extract is loaded, Layla saves a cohort, and Nadia calls Ahmed (member m133, top of the worklist).

The extract is kept as receivedEvery row lands in src_member_row unchanged; member_feature holds the typed values rules run on. Bad values are emptied and logged in data_issue, never guessed.
One care-plan need = one actionaction.need_id points at a care_plan_need. A unique index allows one care-plan action per need. Closing either one writes an outcome and closes the other.
Outcomes are the only way backThe portal never edits signal or assessment. It inserts outcome rows. The nightly run reads the unprocessed ones and stamps processed_at.
